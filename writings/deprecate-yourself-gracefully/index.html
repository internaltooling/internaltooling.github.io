Deprecate yourself gracefully

A system that needs you every week is not a system; it is a pet with a config file. This memo proposes a staged, reversible plan for making yourself unnecessary to everything you run.

Summary

Software has a well-understood ceremony for retiring things: you announce the deprecation, you keep the old path working, you log a warning, and one day the path is gone. People survive it. This RFC applies the same ceremony to a component that has been in maintenance mode for a while and whose absence of tests is becoming a liability: the operator.

To be clear about scope: this is not about leaving. It is about being optional. The difference between those is the difference between a service that pages you and a service that quietly did the thing while you were at the seaside, confused by the lack of notifications.

The problem with being needed

Being needed feels like value, and in a job it sometimes is. In a self-run system it is a smell. Every hour of presence a system demands is an hour the system has quietly borrowed from a future version of you that had other plans. If a week of your absence would lose data, the system is not run by you — you are running for it.

The test is boring on purpose: go somewhere with bad reception. What breaks? The list is the deprecation backlog. Everything on it is a place where the system still believes you are a component.

Proposal

Deprecation proceeds in stages, with the usual promises of support throughout:

  1. Announce (week 0). Write down, per service, the exact conditions under which it is allowed to contact a human. Everything else goes to a log nobody reads, which is where it belonged.
  2. Shim (weeks 1–4). Keep doing the manual steps, but do them by running the script you should have written. If the script does not exist, the step is now: write the script. You are your own compatibility layer.
  3. Warn (weeks 5–8). The scripts move to timers. You are still on call, but only for exceptions the machine genuinely cannot classify. This stage is uncomfortable in the specific way that matters.
  4. Remove (week 9+). The default becomes: nothing waits for you. Presence becomes a bonus feature, not a dependency. You may still intervene — the way one may still hand-wash dishes that the dishwasher already cleaned.

Rollback

Deprecating yourself is reversible, which is what makes it safe. The rollback procedure is to get interested again. This will happen at least twice and is not a failure of the plan; it is the plan operating with a leaky abstraction.

Objections

“The machine does it worse.” Usually true and mostly irrelevant. A 90%-as-good outcome that happens without you beats a 100% outcome that has your Saturday in it. Reserve perfection for the two things where it pays.

“I enjoy the tinkering.” Then the design goal is not less tinkering — it is optional tinkering. A system you may tinker with, and may equally leave for a month, is strictly better than one that schedules your tinkering for you, at night, in a panic.

Status

Experimental. Currently between stages two and three, which those who know the author will recognise as the permanent condition.
