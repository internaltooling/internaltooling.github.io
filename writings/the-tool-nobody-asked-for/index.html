The tool nobody asked for

Every few weeks I build a tool to solve a problem that did not exist until I wanted to build the tool. This document stops pretending that is an accident.

Summary

This memo describes a recurring pattern: a small inconvenience is noticed, a smaller tool is designed, and six weekends later the tool has a plug-in system. The pattern is not a bug. It is the entire business case for the hobby. This RFC proposes accepting the loop, naming it, and keeping the blast radius small.

Central to the proposal is a distinction between problems that need solving and problems that need having. A flat tyre needs solving. A folder of 40,000 files that could, in principle, be renamed according to a scheme you have not yet invented — that is a habitat. Tools built for habitats are different from tools built for tasks, and they should be judged differently: not by whether they finish the job, but by whether they keep the rain out.

Motivation

The immediate motivation was a Saturday. I had eleven things to do and did none of them, because I spent the day writing a script that renames screenshots. The script works. It has flags. One of the flags is --dry-run-but-for-real, whose behaviour is identical to --dry-run. I am not proud, but I am finished, which is more than I can say for the eleven things.

Give someone a tool and they have a tool. Let them build the tool and they have a reason to avoid the task forever.

Non-goals

  • This document does not propose building fewer tools. That has been proposed before, in RFC-0000, which was never filed because I was busy building a tool.
  • It does not define a standard for tool quality. The standard is: would past-me, finding it with no README, forgive present-me?
  • It does not exclude the possibility that the tool becomes useful. That is regarded as an acceptable outcome of the hobby, like a lottery ticket that occasionally pays.

Proposed design

The lifecycle of a tool nobody asked for has five observable stages. Monitoring them is cheaper than resisting them:

itch ──▶ sketch ──▶ build ──▶ polish ──▶ habitat
          (1h)      (1d)     (1-6 wk)   (forever)
                            │
                            └─▶ abandoned ──▶ guilt ──▶ itch

Stage four is where the damage happens. Polishing is indistinguishable from work from the inside, which is exactly why it is so attractive. The proposal is to cap stage four at two sessions: after the second session, the tool ships as-is, warts documented, and joins the habitat.

Alternatives considered

Do nothing. Considered annually, every January. Rejected for lack of a tool to help with it.

Use an existing tool. Rejected on the grounds that the existing tool was built by someone else, for their habitat, and therefore does not have the flag I would have added.

Drawbacks

The main cost is opportunity cost, which is invisible and therefore free. Secondary costs include disk space, one domain name per good mood, and the specific shame of a README that says TODO: everything in a repository with 214 commits.

Status

Accepted. Implementation, as always, is already complete and was the point.
